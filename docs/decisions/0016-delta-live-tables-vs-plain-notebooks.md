# ADR-0016: Delta Live Tables (SQL), not plain PySpark/SQL notebooks, replacing dbt

**Status:** Accepted
**Date:** 2026-08-19

## Context

The dbt project (`dbt/models/`: 8 staging + 5 intermediate + 6 marts, 19 models total, plus dbt tests and two model contracts) is this project's real analytical core -- VWAP/repricing reconstruction, the independent-vs-single-select MULTIPLE_CHOICE resolution logic, the three strict kickoff-time regex patterns, all validated and documented across ADRs 0005-0014. Porting it needed a real answer to two questions: build it as Delta Live Tables (declarative, dependency-graph-managed, with a native data-quality primitive) or as plain PySpark/Spark SQL notebooks run as Job tasks (closer to how the ingestion/flatten step already works); and, having chosen DLT, how each of dbt's test types maps onto DLT's expectation model, since the two aren't the same feature.

## Decision: DLT (SQL), not plain notebooks

**Delta Live Tables (Spark Declarative Pipelines / Lakeflow), written in SQL, one file per dataset** (`databricks/src/pipelines/worldcup/transformations/{staging,intermediate,marts}/*.sql`), a direct, faithful, file-for-file port of the 19 dbt models. SQL, not Python: every dbt model is already SQL, so this is the closer, lower-risk port (see Databricks' own guidance: "Simple pipeline... SQL (simpler, use it as default)"). DLT's own dependency-graph execution and its `EXPECT` primitive are the closest real analog to dbt's `ref()`-based DAG and its generic tests -- plain notebooks would have meant hand-rolling both.

**Materialized Views for all 19 datasets, none as Streaming Tables** -- including `stg_manifold_bets`, the one dbt model that's deliberately incremental. The bronze Delta tables `flatten_to_delta.py` writes are fully overwritten (`.mode("overwrite")`) on every ingestion run, not a genuinely incrementally-arriving file stream; a Streaming Table's append-only, exactly-once semantics would misrepresent what's actually happening to the source data. This is a real, deliberate divergence from the dbt original, not an oversight -- the underlying data here is a one-time tournament backfill (same framing the dbt model's own comment already gives), and MVs correctly recompute from scratch on every pipeline update, which is what this source actually needs.

## The dbt-test-to-DLT-expectation mapping, verified against the real pipeline run, not assumed

| dbt test | DLT port | Verified? |
|---|---|---|
| `not_null` | `CONSTRAINT ... EXPECT (col IS NOT NULL) ON VIOLATION FAIL UPDATE` | Direct, clean port. Confirmed working -- the pipeline reached `COMPLETED` with these active on every model. |
| `accepted_values` | `CONSTRAINT ... EXPECT (col IN ('a', 'b')) ON VIOLATION FAIL UPDATE` | Direct, clean port. Confirmed working (`int_all_market_ticks.source_platform`, `mart_platform_calibration_comparison.source_platform`). |
| Singular test (`assert_kickoff_match_validated_against_known_good.sql`) | Inlined as a row-level `CONSTRAINT` on `int_market_kickoff_times`: `EXPECT (answer_id IS NOT NULL OR manifold_kickoff_at IS NULL OR manifold_kickoff_at = openfootball_kickoff_at)` | Confirmed working -- this is a genuinely row-level check (the dbt original is too, just expressed as a singular SQL test returning violating rows), so it ports cleanly. |
| `unique` / `dbt_utils.unique_combination_of_columns` | **No native DLT equivalent** -- expectations are row-level only, no dataset-level aggregate check. Ported via a `COUNT(*) OVER (PARTITION BY ...) = 1` window column (named `dedup_ok`, kept visible in the output, not hidden) referenced by a plain `CONSTRAINT ... EXPECT (dedup_ok) ON VIOLATION FAIL UPDATE`. | Confirmed working on every model that needed it (all 19). This is a real technique, not a workaround left broken: window functions are fine *inside the SELECT*, just not (confirmed below) inside the `EXPECT` expression itself. |
| `relationships` (referential integrity) | Attempted as `CONSTRAINT ... EXPECT (col IN (SELECT col FROM sibling_table)) ON VIOLATION FAIL UPDATE`. **Confirmed broken, not just untested**: this reliably makes the *constrained table's own* flow resolution fail with `TABLE_OR_VIEW_NOT_FOUND` on the referenced sibling table, even though that sibling is a real dataset in the same pipeline that does get built. A subquery inside an `EXPECT` clause doesn't register as a real dependency edge in DLT's DAG the way a `FROM` clause reference does, so the constrained flow gets analyzed before its subquery dependency is guaranteed to exist. **Removed from every mart that had it** (`mart_market_efficiency`, `mart_match_price_history`, `mart_outright_odds_over_time`, `mart_pre_kickoff_calibration`, `mart_trade_calibration`), documented as a genuine, unresolved DLT gap -- not silently dropped, and not forced to work with a hack. | Confirmed broken by two real failed pipeline runs before removal fixed it. |
| Model contract (`contract: enforced: true`) | Explicit `CAST`s in the `SELECT` list; Delta's schema-on-write does the rest. | Not a DLT feature at all -- dbt's contract enforcement has no DLT analog to test, this is just standard SQL type discipline, same as the rest of the port. |

## A real, separate SQL-dialect finding along the way

**Regex escaping is opposite between DuckDB and Spark SQL.** DuckDB's string literals pass backslashes through unmodified (`'\s'` in a DuckDB SQL string is a literal backslash + `s`, correctly read by the regex engine as "whitespace"). Spark SQL's string literals *do* process backslash escapes, so the same single-backslash pattern silently loses its regex meaning (`\s` gets parsed down to a bare `s`). Confirmed directly against the live SQL warehouse before trusting it in the pipeline (`rlike` with a single backslash pattern returned `false` on a string it should have matched; the doubled-backslash version (`\\s`) returned `true`), not assumed from either engine's general reputation. `int_market_kickoff_times.sql`'s three regex patterns all use doubled backslashes for this reason -- a real, necessary divergence from the DuckDB original, not a copy-paste error.

**Spark SQL's `regexp_extract`/`rlike` otherwise have the same signature as DuckDB's `regexp_extract`/`regexp_matches`**, so the DuckDB-only restriction the original `int_market_kickoff_times.sql` carries (`enabled = target.type != 'postgres'`, because Postgres's regex functions have a different shape) does **not** carry over to this Databricks port. Confirmed by actually running the model, not assumed: it built successfully as part of the same pipeline run that reached `COMPLETED`.

## Two real bugs found only by actually running the pipeline, not by reading the SQL

**Bare sibling-table references resolve against the pipeline's default schema, not the referencing file's own schema.** This project's DLT pipeline spans three schemas (`staging`, `intermediate`, `marts`), with `staging` as the pipeline's declared default `target`. Databricks' own SDP documentation says a sibling dataset should be referenced by bare name "regardless of its own schema" -- true only, it turns out, when every dataset in the pipeline shares one schema. The first real run failed with `TABLE_OR_VIEW_NOT_FOUND` on every intermediate/marts model that read another intermediate/marts model by bare name (e.g. `int_market_implied_probability` reading `int_all_market_ticks`), because Spark resolved the bare name against `staging` (the pipeline's default), not `intermediate` (where the table actually lives). Fixed by fully qualifying every cross-schema `FROM`/`JOIN` reference (`${catalog}.staging.stg_x`, `${catalog}.intermediate.int_y`) throughout every intermediate and marts file, not just the `CREATE` target. A real, load-bearing behavior this port only found by running it and reading the actual error, not by trusting the documented convention.

**The `relationships`-as-subquery `EXPECT` failure above**, found the same way: two real, informative failed pipeline updates (`TABLE_OR_VIEW_NOT_FOUND` on a sibling table that genuinely exists) before removing the constraint fixed it.

## Consequences

**Gained:** all 19 dbt models faithfully re-implemented, the pipeline reaching a real `COMPLETED` state with real data flowing through every layer (verified row counts and expectation results in `databricks/docs/results-databricks.md`), and a concrete, tested map of exactly where DLT's expectation model is and isn't a real substitute for dbt's test suite -- not a hand-wavy "DLT tests are basically the same as dbt tests" claim.

**Cost:** every model with a uniqueness check carries a visible `dedup_ok` marker column dbt's own tests never added to output -- a real, honest tradeoff, not hidden. Referential-integrity checking is gone entirely on this platform for now, a genuine regression in test coverage versus the dbt original, named plainly rather than glossed over.

**Not done:** finding or building a working DLT-native referential-integrity check (e.g. a separate validation flow that isn't itself constrained by the subquery-dependency bug, or an `EXISTS`-based rewrite tried and also found to fail the same way) -- flagged as real follow-up work, not attempted here once the subquery approach was confirmed broken twice.
