# ADR-0014: Semantic cross-platform market matching, local embeddings + local LLM (RAG), not an API

**Status:** Accepted
**Date:** 2026-08-08

## Context

`mart_platform_calibration_comparison` (ADR-0013) compares exactly one hand-picked market pair between Manifold and Polymarket: the outright World Cup winner market on each side, hardcoded as `manifold_outright_market_id`/`polymarket_outright_market_id`. Team-name matching within that one pair is a 2-entry `TEAM_ALIASES` dict in `analysis/compare_platform_predictions.py`, correctly documented there as fine at that scale.

The real, unaddressed gap: Manifold has 621 markets, Polymarket has 6,359 (negRisk fan-out, ADR-0011). There are almost certainly more genuinely comparable market pairs beyond the outright winner (a single team appears in dozens of differently-typed markets on both platforms: outright winner, group-stage advancement, top scorer, exact-date props), but no way to find them at scale except manually eyeballing thousands of market questions. This adds a real RAG pipeline, retrieval (embeddings + cosine similarity) and generation (a local LLM reasoning over retrieved candidates), to surface candidate pairs for human review, without auto-trusting anything into a mart.

## Decisions

**Local `sentence-transformers` (`all-MiniLM-L6-v2`) for embeddings, local Ollama (`qwen2.5:7b`) for generation, neither an API.** This project has zero API-key credential plumbing anywhere, and adding it just for this feature would be a bigger, separate decision than the feature itself warrants. Confirmed both work end to end before committing to the approach, not assumed: `sentence-transformers`/`torch` installs and runs cleanly on the native arm64 Homebrew Python; Ollama installs, pulls a model, and answers real prompts correctly. "Local, no API key" needs one honest qualifier: the first run of each still needs internet, to download the embedding model (~80MB, Hugging Face Hub) and the LLM weights (~4.7GB, Ollama's own registry), a one-time cost, not a per-query one.

**Brute-force numpy cosine similarity, not a vector DB or DuckDB's VSS extension.** At ~7,000 total rows across both platforms, a single `(n_query, 384) x (384, n_candidate)` matmul runs in under half a second (0.24-0.38s measured on the full corpus). No infrastructure this workload's actual scale doesn't justify, the same reasoning ADR-0002 already applied to Spark and `docs/project_scale_vs_production.md` generalizes.

**A real, unplanned detour: this machine's Python has been running under Rosetta emulation this whole project.** Installing `sentence-transformers` against this project's actual `venv/` failed outright (`torch` has no distribution for that interpreter). The instinctive read, "torch doesn't support this Python version yet," was wrong: `torch`'s own PyPI metadata publishes real `cp314` wheels, `macosx_14_0_arm64` only. `file venv/bin/python3.14` confirmed the real cause: this project's `venv/` is Homebrew's Intel build, running under Rosetta on this Apple Silicon Mac, the same two-parallel-Homebrew-installs bug already documented in `requirements.md` for Docker Desktop, just never caught for Python itself, and quietly explains a "Rosetta binary translation... performance degradation" warning DuckDB has been printing unremarked-on all project. Fixed for this feature with a dedicated arm64 venv (`venv-semantic-matching/`, `requirements.md`); rebuilding the main project `venv/` the same way is real, separate follow-up work, flagged but not bundled into this feature.

**Scope boundary: this does not feed `mart_platform_calibration_comparison` in v1.** Discovered pairs are surfaced with similarity scores and LLM-generated reasoning for human review. A wrong auto-trusted match would silently corrupt a mart that feeds a significance test (ADR-0013's own carefulness), and, per the Results below, generation is nowhere near reliable enough yet to auto-trust anyway.

## Two real bugs found and fixed while building this, not shipped unnoticed

**1. `embed_text` design first collapsed every market about the same team into an identical embedding.** The first version embedded the bare team name alone (`coalesce(answer_text, question)`), reasoning that concatenating a shared question prefix onto every one of a market's ~50 answers would dilute the one signal distinguishing them (the team). True within one market's answers; wrong at full-corpus scale. A single team appears in dozens of differently-typed markets (Spain to win outright, Spain to finish 3rd, Spain to reach the final, ...), and every one of them reduces to the identical bare string "Spain", literally tied at cosine similarity 1.0. Caught by actually running the real pipeline, not by inspection: `find_candidate_market_matches.py`'s top-5 for real outright-winner queries turned out to be an arbitrary tied subset of same-team markets, and `explain_top_candidate_matches.py`'s LLM correctly noticed none of its 5 arbitrary candidates said "win outright" and abstained, for teams where a real matching market plainly existed (89/100 abstentions on the first run). Fixed by embedding `question + " [" + answer_text + "]"` instead, confirmed directly before trusting it: "Will Spain win the World Cup? [Spain]" scores 0.903 against "Will Spain finish 3rd? [Spain]" (same team, different type) and 0.757 against "Will Portugal win the World Cup? [Portugal]" (different team, same type), both correctly below the 0.857 two differently-worded versions of the true same-team-same-type question score against each other. Real separation on both axes, not a tie. Re-run after the fix: top-1 retrieval scores across the full corpus dropped from a `median: 0.7202` dominated by degenerate 1.0 ties to a `median: 0.7112` with a real, meaningful spread (`p90: 0.8722`, `p10: 0.5239`), and the top-20 highest-confidence pairs became genuinely specific, correct matches (`"Will France win the 2026 FIFA World Cup?" <-> "Will France win the 2026 FIFA World Cup? [France]"`, 0.9832) instead of bare team-name ties.

**2. The generation prompt's text formatting measurably changed whether the model could confirm an exact, correct match.** Three formats tested on the identical case before choosing one, not assumed: a bare team name alone gave the model no context, and it refused to confirm even an exact match; a `"question (answer)"` parenthetical string made the model read the appended team name as literally redundant, suspicious text (`"this includes '(Spain)' which is redundant"`) and refused again; two clearly labeled fields (`"Market question: ..."`, `"Specific answer: ..."`) fixed both failures completely, confirmed on the same test case all three ways.

## Model size and determinism, also found empirically

`qwen2.5:3b` consistently answered NONE on the one market this feature is actually evaluated against, whose own title is `"2026 FIFA World Cup ⚽ | 🏆 Winner"`, terse and emoji-decorated rather than a full sentence, even with an explicit prompt instruction about terse/stylized titles added specifically to address it. `qwen2.5:7b` got the identical case right immediately. Separately, at the default sampling temperature, `qwen2.5:7b` answered the same hard case correctly 2 of 3 identical, back-to-back calls, and wrong once: real, measured non-determinism, not assumed stable after one success. Set `temperature=0` for `evaluate_candidate_matches.py`'s runs: this doesn't make the model *right*, it makes it consistently whatever it is, which is the property an eval harness needs to be trustworthy run to run. At `temperature=0`, the model reproducibly gets this one specific case wrong, every time, a real, named limitation, not hidden.

## Result

Evaluated against the outright World Cup winner group, ground-truth counts derived at runtime by re-querying the staging tables directly (not hardcoded, and not identical to the 47/50 documented in ADR-0013: that count comes from the mart, which additionally requires a team to have real pre-tournament price ticks; this evaluation queries `stg_manifold_market_answers`/`stg_polymarket_markets` directly, a superset). **49 Manifold teams (50 raw answers minus the "Other" catch-all), 60 Polymarket rows.** The Polymarket side includes 9 genuine placeholder markets (`"Will Team AG win the 2026 FIFA World Cup?"`, `answer_text = "Team AG"`, resolved `NO`), real artifacts of qualification slots not yet assigned to a named country when those markets were created, later superseded once a real team qualified. **48 positive pairs** (teams present on both platforms), **12 negative pairs** (Polymarket-only, 8 of them the nonsense placeholders above plus Bosnia-Herzegovina, "Other", Peru).

Every candidate ranked against the full cross-platform universe (all 6,359 Polymarket rows per positive query, all ~4,766 Manifold rows per negative query), not the 50-row subset, so the number reflects the actual full-corpus difficulty.

| | Result |
|---|---|
| Retrieval hit@1 (48 positives) | **48/48, 100%** |
| Retrieval hit@5 | **48/48, 100%** |
| Generation correct (48 positives, picked the true match from its own top-5) | **28/48, 58%** |
| Generation false positives (12 negatives) | **1/12** |

**Retrieval alone is perfect on this task. Adding the LLM reasoning step on top makes results worse, not better.** The one false positive and the 20 missed positives share a pattern with the Norway case, checked directly, not assumed representative: candidate 1 for `"Will Norway Win The 2026 FIFA World Cup?"` was the correct match, `"Will Norway win the 2026 FIFA World Cup? [Norway]"`, at 0.982 similarity, and the model's own stated reasoning claimed the candidate "does not specify that it's the entire tournament", a plain misreading of text it was directly handed, not an external fact it got wrong. Across the top-100 highest-confidence discovery pairs (a separate, larger sample than the 48/12 ground truth above), every one of the 74 abstentions had a rank-1 retrieval score in the 0.90-0.95 band; the 26 the model confirmed were essentially all >0.95, near-identical wording. The model appears to have an implicit, fairly sharp threshold: near-literal text match gets confirmed, anything requiring recognizing paraphrase or synonymy gets rejected, even when a human reading the same two sentences would call it obviously the same event.

Positive top-1 retrieval scores ranged 0.760-1.0 (median 0.796); negative best-scores ranged 0.648-0.897. These ranges genuinely overlap (0.760-0.897), meaning a naive fixed similarity threshold couldn't cleanly separate confident-correct from confident-wrong either, the actual reason an LLM judgment layer is worth having in principle, even though this specific model/prompt combination under-delivers on it in practice.

## Consequences

**Retrieval, on its own, is the real, usable deliverable here.** `find_candidate_market_matches.py`'s output is trustworthy at rank 1 for genuine matches (100% hit@1 on the ground truth this can be checked against) and is what should be used for human review of new candidate pairs today, not the LLM-filtered output.

**Generation, as built, adds risk more than it adds value, and should not be trusted unreviewed.** This isn't a claim that LLM reranking over retrieved candidates can't work here, it's a claim that this specific prompt/model combination, measured honestly, currently makes the pipeline's precision *worse* than doing nothing past retrieval. A stronger model, few-shot examples of the exact "paraphrase vs. genuinely different market" distinction, or restructuring the question ("does candidate N describe the same real-world outcome" per-candidate rather than "pick the best of 5") are the natural next things to try, not attempted here: this ADR reports what was actually measured, not a tuned-until-it-looked-good number.

**Not done:** improving generation accuracy past 58%; wiring any discovered pair, however confident, into `mart_platform_calibration_comparison`, which given generation's real false-positive rate would be a genuine regression risk to a mart that feeds a significance test; running this at the 100-row (or larger) scale against ground truth rather than the 48/12 outright-winner group, the only group with real ground truth available; rebuilding the main project `venv/` off the Intel Homebrew Python (separate, flagged follow-up).
