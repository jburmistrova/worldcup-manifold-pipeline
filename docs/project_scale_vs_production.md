# This Project vs. a Real Company's Data Engineering Needs

Several ADRs each admit, individually, that some piece of this project is more infrastructure than the workload strictly needs. This doc pulls those admissions into one place, dimension by dimension, so the whole picture is visible at once, rather than pieced together across files. Each row links to the ADR with the full argument; this is the consolidated summary, not a replacement for them.

The point of writing this down explicitly: knowing exactly which corners were cut, and why the full version would look different, is worth more in an interview than pretending a laptop project is production-scale.

| Dimension | This project | At a real company, and why | Reference |
|---|---|---|---|
| **Orchestration** | Standalone Python scripts, run manually, in sequence, by me. | An orchestrator (Airflow, Dagster) manages scheduling, retries-with-context, backfills, and dependency graphs across tasks, often triggering containers on Kubernetes or ECS rather than running scripts directly. Ingest -> Spark -> dbt would be 3 DAG tasks, not 3 scripts run by hand. | Discussed inline; no dedicated ADR. |
| **Spark** | Runs `local[*]` (one laptop simulating a tiny cluster with its own cores) on ~1.2M rows / a few hundred MB. Does extract+load only (parse, select, write Parquet), no real transformation. | Earns its place at genuine multi-TB+ volume beyond one machine's capacity, when the warehouse can't read raw files directly (so a separate load step is required regardless), when multiple consumers beyond one dbt project need the same clean data layer, or as an organizational boundary between a data engineering team and an analytics engineering team. None of these apply here: one consumer, no existing platform, one person. | [ADR-0002](decisions/0002-spark-despite-small-data-volume.md) |
| **Kubernetes** | A single-node local cluster (minikube/kind) running one Job. | Earns its place across many machines and many workloads: bin-packing for cost efficiency, self-healing when *some* machine in a large fleet inevitably fails, one shared operational model across many teams, autoscaling under real load spikes. A single-node cluster can't demonstrate any of this. What's actually practiced here is the declarative Job API and the `kubectl` debugging workflow, not the scale-driven value. | [ADR-0003](decisions/0003-kubernetes-job-not-cronjob-or-deployment.md) |
| **Data warehouse** | DuckDB: embedded, file-based, no server, one user. | A real analytics warehouse (Snowflake/BigQuery/Redshift, or Postgres for smaller cases) serves many concurrent users and queries, needs access controls, cost management, and query-performance tuning at a scale DuckDB was never built for. The planned Postgres-as-StatefulSet phase is explicitly about Kubernetes stateful-workload practice, not about needing a "real" warehouse for this data. | [ADR-0004](decisions/0004-local-warehouse-duckdb-then-postgres.md) |
| **Batch vs. streaming** | A one-time backfill over a finished tournament. Everything is already resolved, historical data. | A live product (an actual sportsbook, a real-time trading system) needs prices to update within milliseconds of new information (a goal, a news event), which means Kafka feeding Spark Structured Streaming, not a batch Job that runs once and stops. Staleness in a live system is a real financial/arbitrage risk; it's a non-issue for a backfill. | README, "What I'd do differently in production" |
| **Data volume** | ~1.2M bet records, 621 markets, a few hundred MB total across all raw files. | Real pipelines at scale-justifying companies routinely handle billions of records and many TB, volumes where single-machine tools (DuckDB, Polars, pandas) genuinely stop being viable regardless of preference, and distributed compute stops being optional. | Ties directly to the Spark and Kubernetes rows above. Most of this project's "why not use the simpler tool" tension traces back to this one gap. |
| **Team structure** | One person did ingestion, transformation design, infrastructure, and analysis. | Real data platforms split this across roles (data engineers for ingestion/infra, analytics engineers for dbt/transformation, data scientists for the analysis, platform/SRE teams for the Kubernetes layer itself), with defined handoffs and ownership boundaries between them. Some of the Spark/dbt split in this project is a technical decision (ADR-0005); at a real company, that same split is often *also* an organizational one. | Ties to the Spark row above. |
| **CI/CD, monitoring, alerting** | CI runs the real pipeline (Spark + full `dbt build`, all tests) on every push, against a small committed fixture rather than the live API. No deploy pipeline, no monitoring, no alerting. Failures beyond CI are visible because I'm the one running it and watching the terminal or `kubectl logs`. | Production pipelines also have automated deploy pipelines, dashboards for freshness/volume anomalies, and paging (Slack/PagerDuty) when something breaks, because nobody is watching a terminal waiting for a multi-team system to fail. | `docs/data_engineering_best_practices.md` |
| **Environments** | One environment: my laptop, plus a local Kubernetes cluster. | Real pipelines separate dev/staging/prod (different dbt targets, different K8s namespaces, different access levels) specifically so a bad change can be caught before it touches real data or real users. Deliberately skipped here as unnecessary ceremony for a solo project. | `docs/data_engineering_best_practices.md` |

## What actually generalizes

Not everything above is a gap to apologize for. The parts of this project genuinely worth defending in an interview are the ones that don't depend on scale at all:

- Reading a data source's actual terms of service before building on it ([ADR-0001](decisions/0001-data-source-manifold-not-kalshi.md)), a scale-independent, still-rare practice.
- The ELT reasoning (dbt owns transformation, Spark owns extract+load) is a real architectural principle, not a toy simplification ([ADR-0005](decisions/0005-elt-not-etl-transformation-lives-in-dbt.md)).
- Raw data immutability, and getting it wrong once before fixing it properly ([ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md)). The lesson doesn't get bigger or smaller with data volume.
- Verifying "duplicates" are actually identical before dropping them, and correctly distinguishing extraction-artifact duplicates from business-logic duplicates. This reasoning is identical whether the dataset is 400 rows or 400 billion.

The scale-dependent tools (Spark, Kubernetes) were practiced deliberately, on a project too small to need them, specifically so the underlying patterns are already familiar before they show up on real, scale-justified data.
