# Data Engineering Best Practices: Applied, Planned, or Deliberately Skipped

A living checklist, updated as the project progresses, not written retroactively to look complete. As of 2026-07-30: market + market-answer ingestion is built; bet-level ingestion, Spark, dbt, and Kubernetes are not yet built. Anything marked "Planned" is a real plan, not a promise. This file gets corrected if reality diverges from it.

For deeper reasoning on any of the "why," see [docs/decisions/](decisions/). This file is the quick-scan checklist; the ADRs are the full argument for the ones that needed one.

Each row cites a real, checkable source where one genuinely exists. Where it doesn't (some of these are general practice without a single canonical origin), that's stated explicitly rather than attaching a citation for the sake of having one. Full list in [References](#references).

## Data ingestion

| Practice | Status | Why | Source |
|---|---|---|---|
| Verify legal/ToS right to use a data source before building on it | **Done** | The entire Kalshi -> Manifold pivot ([ADR-0001](decisions/0001-data-source-manifold-not-kalshi.md)): read the actual governing documents rather than assuming "public API" meant "free to use for this." | *No single canonical source. General professional/legal due diligence, grounded here in Kalshi's and Manifold's own published terms, cited directly in ADR-0001.* |
| Respect rate limits, back off on failure | **Done** | Both ingestion scripts sleep between requests, staying well under Manifold's 500 req/min limit. | [1] AWS Architecture Blog, *Exponential Backoff and Jitter* |
| Idempotent re-runs (no duplicate accumulation) | **Done, with a caveat** | Both scripts open their output CSV in overwrite mode (`"w"`), so re-running produces a fresh, consistent snapshot rather than appending duplicates. That's correct for a one-time backfill, but it's a **full-refresh** pattern, not true incremental idempotency (e.g. "only fetch markets created since last run, upsert by ID"). That distinction matters and is called out explicitly rather than claiming more than what's actually built. | [2] Stripe Docs, *Idempotent requests*; [3] Kleppmann, *Designing Data-Intensive Applications*, Ch. 11 |
| Don't assume upstream schema, verify empirically | **Done** | Confirmed timestamp units (epoch ms, UTC) by converting real values rather than assuming; discovered `MULTIPLE_CHOICE` markets carry no top-level `probability` and their `resolution` is an opaque answer ID, not a label. Documented in [docs/data_dictionary.md](data_dictionary.md) instead of silently mishandling it. | *No external citation. This row is evidenced by our own discovery process, not an outside authority.* |
| Verify a keyword search actually scopes to what you assume it does | **Done, after a real finding** | The ingestion search term `"World Cup 2026"` isn't scoped to football at all. At least 3 ingested markets turned out to be about the Cricket T20 World Cup, sharing team codes (`IND`, `ENG`) with real football teams. Found while building kickoff-time matching ([ADR-0008](decisions/0008-kickoff-time-enrichment-openfootball.md)), not by inspecting the data beforehand. Confirmed harmless for that specific matcher, since a cricket-only code doesn't resolve against the football schedule, so it fails safe rather than producing a wrong cross-sport match, but a keyword search is a filter on text, not on topic, and shouldn't be assumed to scope to the intended subject without checking. | *No citation needed. Evidenced by this project's own discovery, not an external claim.* |
| Don't trust automatic schema inference for numeric types, cast explicitly | **Done, after a real bug CI caught** | `spark/flatten_to_parquet.py` relied on Spark's schema inference for every field, including a docstring claim that this was safe "because JSON is self-describing." It isn't, for numeric columns specifically: inference guesses a column's type from a *sample* of its actual values, not from a fixed contract. On the small CI fixture, every `totalLiquidity` value happens to be a whole number, so Spark inferred `BIGINT`; on the full dataset, fractional values (`142.857...`) make it infer `DOUBLE`. Same field, same source, different type depending on which rows were in the sample. Broke `mart_market_efficiency`'s enforced dbt contract (`data_type: double`) the first time CI actually ran against the fixture, on GitHub, not locally. Fixed by explicitly casting every real-valued business field to `DOUBLE` in the Spark step, rather than trusting inference for them. | *No external citation. Evidenced by this project's own bug, caught by CI doing exactly what it's for.* |
| Handle upstream API changes gracefully (schema drift) | **Not done** | No schema validation layer on ingestion. If Manifold changes a field name, the scripts would likely fail loudly (a `KeyError`) rather than degrade gracefully. Acceptable for a one-time backfill against a stable, versioned public API; would not be acceptable for a long-running production pipeline, where I'd add explicit schema validation (e.g. Pydantic models or a `pandera`/`great_expectations` check) at the ingestion boundary. | *General engineering practice. No single canonical source found; declining to force one.* |
| Verify pagination *completeness*, not just correctness of what came back | **Done, after a real bug** | Found and fixed a second, distinct pagination bug beyond the earlier duplicate-rows one ([ADR-0007](decisions/0007-search-limit-truncation.md)): a small `limit` (100) was silently truncating results. 232 of 621 real markets (37%) missing, with zero errors raised and zero variance across repeated runs, so nothing about the failure looked like a failure. Caught by cross-checking the paginated loop's total against an independent single large-`limit` call, not by the loop itself ever signaling a problem. The lesson: a paginated fetch completing without errors is not evidence it's complete. Verify the count against an independent method. | *General practice, not a single canonical/primary source. Several similar secondary write-ups exist, declining to cite one as if authoritative.* |
| Raw/landing data is immutable, never mutated in place | **Done, after getting it wrong first** | Fixed a duplicate-row bug by deduplicating and overwriting the raw CSVs directly. A real mistake, not a hypothetical one. The original files (duplicates and all) are gone. Fixed properly per [ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md): raw is now write-once; corrections happen at extraction time or via a fresh run, never by rewriting a landed raw file. Left this row honest about the mistake rather than only describing the end state. | [11] Databricks, *Medallion architecture*: "Bronze Layer... No data cleanup or validation is performed here" |
| Capture full raw payloads, don't pre-select fields at ingestion | **Done** | The original CSV scripts hand-picked a `FIELDS` list per file, which meant "raw" was already a curated projection, not the true API response. Switched to JSON Lines with the complete, unmodified object per record ([ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md)). Paid off twice now: fields we didn't know existed (`pool`, `mechanism`, `uniqueBettorCount`, a `url` field we'd been reconstructing manually) were captured for free the first time; later, investigating a completely unrelated question (pre-kickoff calibration) turned up `sportsStartTimestamp` sitting in data we'd already ingested weeks earlier ([ADR-0007](decisions/0007-search-limit-truncation.md)). No re-ingestion needed to discover it, because it was never thrown away in the first place. | [11] Databricks, *Medallion architecture* |
| Enrich gaps in a primary source from external or existing data, but validate the join before trusting it | **Done, validated with an exact match** | `sportsStartTimestamp` (a real, precise kickoff time) covered only a fraction of markets, closing off a full-dataset pre-kickoff calibration analysis (ADR-0007). Found `openfootball/worldcup.json`, a CC0-licensed schedule with exact kickoff times, verified via GitHub's own license API and the actual `LICENSE.md`, not just a README claim. The real risk, raised before writing any matching code: a naive join on team-name mentions in free text would produce false positives, not just missing data. A market like "Will Norway advance to the quarterfinals?" mentions a team but isn't about any single game; attaching a kickoff time to it would be silently wrong, worse than an honest gap. Investigated empirically first: of 621 markets, only 108 already carried `sportsStartTimestamp` in one strict, machine-parseable format; checking coverage against that population directly (not just trusting the first pattern's count) turned up 1 more genuine match-market in a second, different format, plus 102 answers nested inside 5 round-aggregator "Mega-Market" questions with no kickoff data from Manifold at all but their own consistent, strict phrasing. Everything else genuinely isn't a single-match question (prop bets, tournament winners, other tournaments, and, found along the way, unrelated Cricket World Cup markets, see the row above) and correctly gets no kickoff time. Built `int_market_kickoff_times` on 3 strict patterns, one per source shape, never one loosened pattern stretched to cover all of them. Validated, not assumed: matched every one of the 108 already-known-good markets against the new logic and got **exact agreement, 108 of 108, 0 seconds off**, before trusting the same matching on the 102 answers with no independent ground truth. That check is now a permanent dbt test (`assert_kickoff_match_validated_against_known_good.sql`), not a one-off. Full reasoning in [ADR-0008](decisions/0008-kickoff-time-enrichment-openfootball.md). | *General data-quality practice, sometimes called entity resolution or record linkage. No single canonical source cited here; declining to attach one without direct verification.* |
| Don't assume the runtime environment already has what a script needs | **Done, after a real bug** | All three ingest scripts (and `analysis/plot_calibration.py`) wrote to a path like `data/raw/...` or `docs/images/...` without ever creating the parent directory. Worked locally only because those directories already existed from early manual setup, months before this row was written. Containerizing for Kubernetes exposed it immediately: a fresh filesystem has none of that leftover state, and every affected script crashed with `FileNotFoundError` on its very first write. Fixed with `os.makedirs(..., exist_ok=True)` before every write, in all four scripts. The general lesson: a script that only works because of state nobody remembers creating isn't actually reproducible, even if it's been running fine locally for a long time. A fresh clone or a fresh container is the real test, not "it works on my machine." | *No citation needed. Evidenced by this project's own bug, not an external claim.* |
| Deduplicate defensively when consuming paginated/unstable APIs, but where depends on the scenario | **Done, with the distinction documented** | Found a real bug: `/v0/search-markets`'s offset pagination isn't guaranteed stable, producing 63 duplicate markets that cascaded into dependent files. Two different categories of "duplicate," handled differently: **(a) artifacts of the extraction mechanism itself** (this case, the source has 388 real markets, our own fetch loop asked for one twice) are reasonable to dedupe *during* extraction, before anything is written. That's what `fetch_all()` does now. **(b) duplicates inherent to the source's actual data** (two genuinely distinct-but-similar records, or "does a cancelled-then-resubmitted order count as one event") are a business judgment call and belong downstream (dbt, tested, visible), same reasoning already applied to the `isFilled`/`isCancelled`/`isRedemption` filtering. Getting this distinction wrong in the other direction (silently dropping business-meaningful "duplicates" at ingestion) would be its own bug. Two things worth being explicit about, surfaced while reviewing this code line by line rather than just writing it: **verify "duplicates" are actually identical before dropping them.** We checked the duplicate rows byte-for-byte equal before deduping; same key but *different* content would be a different, scarier problem (a real data conflict, not a redundant fetch) needing different handling entirely, not a silent drop. And **don't frame pagination instability as "their API's bug."** Offset pagination combined with a non-strictly-ordered sort (ties in relevance ranking) is a well-known general limitation of that pattern, not a defect specific to this API. The defensible framing is "a careful client defends against this regardless of whose API it is," not "working around their mistake." The second framing reads as blame-shifting under a follow-up question. | *No single canonical source for the scenario split. Reasoning is [ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md)'s own, informed by the same logic as [ADR-0005](decisions/0005-elt-not-etl-transformation-lives-in-dbt.md).* |

## Data quality & testing

| Practice | Status | Why | Source |
|---|---|---|---|
| Automated data-quality tests (bounded values, uniqueness, referential integrity) | **Done** | 28 dbt tests across staging, intermediate, and marts: probabilities bounded 0-1 (singular tests per model), no duplicate/null bet IDs, VWAP bounded, mart output bounded. All passing on every `dbt build`. | [4] dbt Labs, *How we structure our dbt projects* |
| Unit tests for transformation logic | **Not done** | The Spark step (`spark/flatten_to_parquet.py`) has no unit tests against small fixture datasets, independent of a running Spark cluster. Lower-risk than it sounds: Spark is deliberately bounded to extract + load only (see ADR-0005), so there's no VWAP/repricing logic living there to test. That logic is in dbt SQL and covered by dbt tests instead. Would still be worth adding if Spark's `.select()`/flattening logic grew more complex. | *General software testing practice. No single canonical source specific to Spark transformation testing.* |
| CI running tests automatically | **Done** | [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs Spark + `dbt build` (all 28 tests) on every push, against a small committed fixture ([`tests/fixtures/raw/`](../tests/fixtures/raw/), 5 real markets, a mix of resolved `BINARY` and `MULTIPLE_CHOICE`, 244 real bet records). Deliberately doesn't call the live Manifold API in CI. This project found that exact API to be slow/rate-limited under rapid repeated calls (see `lessons_learned.md`), so depending on it in CI would trade a fast, reliable check for a flaky one, on top of there being no reason to re-pull ~600 markets on every push. | [5] Fowler, *Continuous Integration*; [6] dbt Labs, *About continuous integration (CI) in dbt* |
| Keep test fixtures in sync when the pipeline's own schema changes | **Known gap, found twice** | A fixed fixture and a growing pipeline drift apart by default, and this project has hit it twice: a `totalLiquidity` type mismatch (all whole numbers in the small sample, forcing `BIGINT` where the full dataset infers `DOUBLE`) and a `sportsStartTimestamp` column absent entirely (none of the fixture's 5 markets happen to be the shape that carries it). Both were fixed at the code level (explicit casts, a defensive optional-column helper), the right fix for those specific bugs, but that doesn't close the actual gap: the fixture still doesn't contain a single market shaped like ADR-0008's clean-format matches or Mega-Market answers, so `int_market_kickoff_times`, `mart_pre_kickoff_calibration`, and `mart_match_price_history` currently build to **zero rows** in CI. Their tests pass, but only because `not_null` and `unique` tests are vacuously true on an empty table, not because CI ever exercises the actual matching logic. Adding a representative example of each new market shape to the fixture whenever the schema grows a new one CI should actually test is still outstanding. | *No citation needed. Evidenced by this project's own bug, twice, and the gap it exposes.* |

## Pipeline reliability & operations

| Practice | Status | Why | Source |
|---|---|---|---|
| Retry logic on transient failures | **Done, across all three ingest scripts** | Started in `pull_bets.py` only, after a real 503 crashed it mid-run on 2026-07-31, 125 markets in. At the time, `pull_markets.py` and `pull_market_answers.py` were left alone on the reasoning "smaller, faster scripts that haven't failed this way." That reasoning turned out to be wrong: containerizing for the Kubernetes phase surfaced a real read timeout in `pull_markets.py` (a `ConnectionError`/`ReadTimeoutError` raised before any HTTP response exists, a status-code check alone can't catch it, since there's no status code yet). Extracted the retry-with-backoff logic into a shared `ingest/retry_get.py`, used by all three scripts, so retry semantics can't drift between them the way "add it where it broke" was starting to produce. 4xx errors are still never retried. Kubernetes' Job `backoffLimit` gives retry at the whole-job level for free on top of this ([ADR-0003](decisions/0003-kubernetes-job-not-cronjob-or-deployment.md)), a different layer (retry the whole run) from this (retry one HTTP call). | [1] AWS Architecture Blog, *Exponential Backoff and Jitter*; [7] Kubernetes Docs, *Jobs* |
| Incremental processing instead of full reprocessing | **Done, as a demonstrated mechanism, not because this project's data actually needs it** | `stg_manifold_bets` is incremental (`unique_key='bet_id'`, filtered on `created_at` past what's already loaded) rather than full-refreshing every run. The largest raw dataset (1.17M+ rows), the one most analogous to a real fact table. Verified both directions, not just configured: a rerun with no new source data adds zero rows (idempotent no-op), and a synthetic late-arriving bet, added directly to the source Parquet, comes through as exactly one new row with no duplication on the next run. Honest framing: this is a one-time historical backfill over a finished tournament, so the data itself never actually grows. The point of building this was to prove the mechanism works correctly, not because ongoing incremental loads are a real requirement here. Would matter for real if this became a live pipeline (see the batch-vs-streaming note in the README). | [4] dbt Labs, *How we structure our dbt projects* |
| Environment separation (dev/staging/prod) | **Deliberately skipped** | Solo project, single environment (my laptop + a local minikube/kind cluster). Multiple environments would be artificial ceremony here. In production I'd want separate dbt targets and probably separate K8s namespaces for dev vs. prod. | [8] Wiggins, *The Twelve-Factor App*: Factor X, Dev/prod parity |
| Alerting on pipeline failure | **Deliberately skipped** | No on-call for a personal batch job. I'm the one running it and can see `kubectl logs` / Job status directly. A production version would push failures to Slack or PagerDuty instead of relying on someone watching. | [9] Google, *Site Reliability Engineering*, Ch. 6, Monitoring Distributed Systems |
| Data retention / deletion policy | **Deliberately skipped** | Small, bounded, one-time dataset (a single tournament), not a continuously accumulating dataset that needs a TTL or archival policy. | *No citation needed. A direct consequence of the project's own scope.* |

## Architecture & code practices

| Practice | Status | Why | Source |
|---|---|---|---|
| Document non-obvious decisions, including tradeoffs given up | **Done** | [docs/decisions/](decisions/): 5 ADRs so far, including the ones where I deliberately added complexity the workload didn't strictly need. | [10] Nygard, *Documenting Architecture Decisions* |
| Use current, actively-supported (non-EOL) runtime versions | **Done** | Started on the system's pre-installed Python 3.8.10 and Java 8, both long past end-of-life, meaning no further security patches. Upgraded to Python 3.14.6 (latest stable) and OpenJDK 25 (latest LTS, not the newest overall release, LTS is what "most stable" actually means for Java's release model). Confirmed compatible with both PySpark and dbt before switching, not after. Full reasoning, version-compatibility check, and a real build failure encountered along the way: [requirements.md](../requirements.md). | [14] Python Developer's Guide, *Status of Python versions*; [15] Oracle, *Java SE Support Roadmap* |
| Secrets never hardcoded or committed | **Done** | `secrets/` and `.env` are gitignored from the start ([.gitignore](../.gitignore)). Currently unused in practice, Manifold's endpoints need no auth, but the pattern was set up before writing any ingestion code, not after. | [8] Wiggins, *The Twelve-Factor App*: Factor III, Config |
| Version control | **Done** | `git init` run 2026-07-30, after several ingestion scripts and docs already existed. The gap was flagged here first, then closed. Left visible in this row rather than edited away. | *Foundational software engineering practice. Doesn't need a citation.* |
| Layered transformation (raw -> staging -> curated), not one monolithic step | **Done** | `stg_manifold_bets`/`stg_manifold_markets`/`stg_manifold_market_answers` -> `int_market_implied_probability` -> `mart_market_efficiency`/`mart_trade_calibration`. | [4] dbt Labs, *How we structure our dbt projects*; [11] Databricks, *Medallion architecture* |
| ETL vs. ELT, where transformation happens | **Decided** | Originally planned to have Spark transform (probability reconstruction, VWAP) *before* landing, then dbt transform again after. An unintentional hybrid that, on inspection, was really ETL wearing an ELT-shaped diagram. The actual test is *where the transform compute runs*, not whether raw data lands before transformation. Resolved in [ADR-0005](decisions/0005-elt-not-etl-transformation-lives-in-dbt.md): Spark is now bounded to extract + load (parse/flatten raw JSON, no business logic); all transformation happens in dbt SQL against the warehouse. | [12] IBM, *ELT vs. ETL: What's the Difference?*; [13] dbt Labs, *Data transformation vs ETL* |
| Pinned, reproducible dependencies | **Done** | Every package in `requirements.txt` is version-pinned (`requests==2.34.2`, `pyspark==4.2.0`, `dbt-core==1.12.0`, `dbt-duckdb==1.10.1`, `matplotlib==3.11.1`), checked and confirmed compatible with the Python version in use before pinning, not after. Same idea applied to dbt's own dependencies: `dbt/packages.yml` pins `dbt_utils` to a version range, and the resolved `dbt/package-lock.yml` is committed (unlike `dbt_packages/` itself, the downloaded package source, gitignored same as `node_modules/`, since it's regenerable via `dbt deps`). | *General Python packaging practice. No single canonical source.* |
| Schema/contract enforcement on published tables | **Done** | Both marts (`mart_market_efficiency`, `mart_trade_calibration`) have `contract: {enforced: true}` with an explicit `data_type` on every column. dbt checks the model's actual output against that list at build time and refuses to build on a mismatch. Verified this isn't just decorative YAML: deliberately changed a column's declared type to the wrong one, confirmed `dbt build` failed with a clear `data type mismatch` error, then reverted. Protects the downstream analysis scripts (`analysis/plot_calibration.py`, `compute_calibration_metrics.py`) from a silent schema change upstream. | [4] dbt Labs, *How we structure our dbt projects* |
| DRY shared logic instead of copy-pasting it across models | **Done, after finding real duplication** | The decile-bucketing expression (`least(floor(x*10)/10, 0.9)`) was independently written out in both `mart_market_efficiency` and `mart_trade_calibration`. A real risk that one gets tweaked later and the other quietly doesn't. Extracted into a shared macro (`dbt/macros/prob_bucket.sql`), used by both models. Verified behavior-preserving by rerunning the full Brier/liquidity analysis after the refactor and confirming every number matched exactly. | *General software engineering practice (DRY). No single canonical source specific to dbt macros.* |

## What's explicitly not a goal of this checklist

Not every real-world practice belongs here just because it exists. E.g. multi-region failover, cost-based autoscaling, or data governance/access-control tooling would be actively strange to build for a one-time personal backfill. Leaving them off isn't an oversight; they're not being tracked as "skipped" because they were never in scope to begin with. The line I'm drawing: track things a data engineer would reasonably expect *this specific project* to have an opinion on, not a maximal checklist of everything a large company's data platform might do.
