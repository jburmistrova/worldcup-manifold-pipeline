# Data Engineering Best Practices — Applied, Planned, or Deliberately Skipped

A living checklist, updated as the project progresses — not written retroactively to look complete. As of 2026-07-30: market + market-answer ingestion is built; bet-level ingestion, Spark, dbt, and Kubernetes are not yet built. Anything marked "Planned" is a real plan, not a promise — this file gets corrected if reality diverges from it.

For deeper reasoning on any of the "why," see [docs/decisions/](decisions/) — this file is the quick-scan checklist; the ADRs are the full argument for the ones that needed one.

Each row cites a real, checkable source where one genuinely exists. Where it doesn't — some of these are general practice without a single canonical origin — that's stated explicitly rather than attaching a citation for the sake of having one. Full list in [References](#references).

## Data ingestion

| Practice | Status | Why | Source |
|---|---|---|---|
| Verify legal/ToS right to use a data source before building on it | **Done** | The entire Kalshi → Manifold pivot ([ADR-0001](decisions/0001-data-source-manifold-not-kalshi.md)) — read the actual governing documents rather than assuming "public API" meant "free to use for this." | *No single canonical source — general professional/legal due diligence. Grounded here in Kalshi's and Manifold's own published terms, cited directly in ADR-0001.* |
| Respect rate limits, back off on failure | **Done** | Both ingestion scripts sleep between requests, staying well under Manifold's 500 req/min limit. | [1] AWS Architecture Blog, *Exponential Backoff and Jitter* |
| Idempotent re-runs (no duplicate accumulation) | **Done, with a caveat** | Both scripts open their output CSV in overwrite mode (`"w"`), so re-running produces a fresh, consistent snapshot rather than appending duplicates. That's correct for a one-time backfill, but it's a **full-refresh** pattern, not true incremental idempotency (e.g. "only fetch markets created since last run, upsert by ID") — that distinction matters and is called out explicitly rather than claiming more than what's actually built. | [2] Stripe Docs, *Idempotent requests*; [3] Kleppmann, *Designing Data-Intensive Applications*, Ch. 11 |
| Don't assume upstream schema — verify empirically | **Done** | Confirmed timestamp units (epoch ms, UTC) by converting real values rather than assuming; discovered `MULTIPLE_CHOICE` markets carry no top-level `probability` and their `resolution` is an opaque answer ID, not a label — documented in [docs/data_dictionary.md](data_dictionary.md) instead of silently mishandling it. | *No external citation — this row is evidenced by our own discovery process, not an outside authority.* |
| Handle upstream API changes gracefully (schema drift) | **Not done** | No schema validation layer on ingestion — if Manifold changes a field name, the scripts would likely fail loudly (a `KeyError`) rather than degrade gracefully. Acceptable for a one-time backfill against a stable, versioned public API; would not be acceptable for a long-running production pipeline, where I'd add explicit schema validation (e.g. Pydantic models or a `pandera`/`great_expectations` check) at the ingestion boundary. | *General engineering practice — no single canonical source found; declining to force one.* |
| Raw/landing data is immutable — never mutated in place | **Done, after getting it wrong first** | Fixed a duplicate-row bug by deduplicating and overwriting the raw CSVs directly — a real mistake, not a hypothetical one. The original files (duplicates and all) are gone. Fixed properly per [ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md): raw is now write-once; corrections happen at extraction time or via a fresh run, never by rewriting a landed raw file. Left this row honest about the mistake rather than only describing the end state. | [11] Databricks, *Medallion architecture* — "Bronze Layer... No data cleanup or validation is performed here" |
| Capture full raw payloads — don't pre-select fields at ingestion | **Done** | The original CSV scripts hand-picked a `FIELDS` list per file, which meant "raw" was already a curated projection, not the true API response. Switched to JSON Lines with the complete, unmodified object per record ([ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md)). Already paid off directly: fields we didn't know existed (`pool`, `mechanism`, `uniqueBettorCount`, a `url` field we'd been reconstructing manually) are now captured for free. | [11] Databricks, *Medallion architecture* |
| Deduplicate defensively when consuming paginated/unstable APIs — but where depends on the scenario | **Done, with the distinction documented** | Found a real bug: `/v0/search-markets`'s offset pagination isn't guaranteed stable, producing 63 duplicate markets that cascaded into dependent files. Two different categories of "duplicate," handled differently: **(a) artifacts of the extraction mechanism itself** (this case — the source has 388 real markets, our own fetch loop asked for one twice) are reasonable to dedupe *during* extraction, before anything is written — that's what `fetch_all()` does now. **(b) duplicates inherent to the source's actual data** (two genuinely distinct-but-similar records, or "does a cancelled-then-resubmitted order count as one event") are a business judgment call and belong downstream (dbt, tested, visible) — same reasoning already applied to the `isFilled`/`isCancelled`/`isRedemption` filtering. Getting this distinction wrong in the other direction (silently dropping business-meaningful "duplicates" at ingestion) would be its own bug. Two things worth being explicit about, surfaced while reviewing this code line by line rather than just writing it: **verify "duplicates" are actually identical before dropping them** — we checked the duplicate rows byte-for-byte equal before deduping; same key but *different* content would be a different, scarier problem (a real data conflict, not a redundant fetch) needing different handling entirely, not a silent drop. And **don't frame pagination instability as "their API's bug"** — offset pagination combined with a non-strictly-ordered sort (ties in relevance ranking) is a well-known general limitation of that pattern, not a defect specific to this API. The defensible framing is "a careful client defends against this regardless of whose API it is," not "working around their mistake" — the second framing reads as blame-shifting under a follow-up question. | *No single canonical source for the scenario split — reasoning is [ADR-0006](decisions/0006-raw-layer-jsonl-immutable.md)'s own, informed by the same logic as [ADR-0005](decisions/0005-elt-not-etl-transformation-lives-in-dbt.md).* |

## Pipeline reliability & operations

| Practice | Status | Why | Source |
|---|---|---|---|
| Retry logic on transient failures | **Partially done** | Kubernetes' Job `backoffLimit` will give this for free once the K8s phase is built ([ADR-0003](decisions/0003-kubernetes-job-not-cronjob-or-deployment.md)). The current standalone ingestion scripts have no retry logic of their own — a transient network error today just crashes the script. Acceptable for now since I'm running them manually and watching; would fix before relying on unattended runs. | [7] Kubernetes Docs, *Jobs* |
| Incremental processing instead of full reprocessing | **Deliberately not done** | This is explicitly a one-time historical backfill over a finished tournament, not a continuously growing dataset — there's nothing to process incrementally. Would matter if this became a live pipeline (see the batch-vs-streaming note in the README). | *No citation needed — a direct consequence of the project's own scope, not an external claim.* |
| Environment separation (dev/staging/prod) | **Deliberately skipped** | Solo project, single environment (my laptop + a local minikube/kind cluster). Multiple environments would be artificial ceremony here. In production I'd want separate dbt targets and probably separate K8s namespaces for dev vs. prod. | [8] Wiggins, *The Twelve-Factor App* — Factor X, Dev/prod parity |
| Alerting on pipeline failure | **Deliberately skipped** | No on-call for a personal batch job — I'm the one running it and can see `kubectl logs` / Job status directly. A production version would push failures to Slack or PagerDuty instead of relying on someone watching. | [9] Google, *Site Reliability Engineering*, Ch. 6, Monitoring Distributed Systems |
| Data retention / deletion policy | **Deliberately skipped** | Small, bounded, one-time dataset (a single tournament) — not a continuously accumulating dataset that needs a TTL or archival policy. | *No citation needed — a direct consequence of the project's own scope.* |

## Architecture & code practices

| Practice | Status | Why | Source |
|---|---|---|---|
| Document non-obvious decisions, including tradeoffs given up | **Done** | [docs/decisions/](decisions/) — 5 ADRs so far, including the ones where I deliberately added complexity the workload didn't strictly need. | [10] Nygard, *Documenting Architecture Decisions* |
| Use current, actively-supported (non-EOL) runtime versions | **Done** | Started on the system's pre-installed Python 3.8.10 and Java 8 — both long past end-of-life, meaning no further security patches. Upgraded to Python 3.14.6 (latest stable) and OpenJDK 25 (latest LTS, not the newest overall release — LTS is what "most stable" actually means for Java's release model). Confirmed compatible with both PySpark and dbt before switching, not after. Full reasoning, version-compatibility check, and a real build failure encountered along the way: [requirements.md](../requirements.md). | [14] Python Developer's Guide, *Status of Python versions*; [15] Oracle, *Java SE Support Roadmap* |
| Secrets never hardcoded or committed | **Done** | `secrets/` and `.env` are gitignored from the start ([.gitignore](../.gitignore)). Currently unused in practice — Manifold's endpoints need no auth — but the pattern was set up before writing any ingestion code, not after. | [8] Wiggins, *The Twelve-Factor App* — Factor III, Config |
| Version control | **Done** | `git init` run 2026-07-30, after several ingestion scripts and docs already existed. The gap was flagged here first, then closed — left visible in this row rather than edited away. | *Foundational software engineering practice — doesn't need a citation.* |
| Layered transformation (raw → staging → curated), not one monolithic step | **Planned** | dbt's `stg_manifold_bets` → `int_market_implied_probability` → marts structure. Not yet built. | [4] dbt Labs, *How we structure our dbt projects*; [11] Databricks, *Medallion architecture* |
| ETL vs. ELT — where transformation happens | **Decided** | Originally planned to have Spark transform (probability reconstruction, VWAP) *before* landing, then dbt transform again after — an unintentional hybrid that, on inspection, was really ETL wearing an ELT-shaped diagram. The actual test isn't whether raw data lands before transformation — it's *where the transform compute runs*. Resolved in [ADR-0005](decisions/0005-elt-not-etl-transformation-lives-in-dbt.md): Spark is now bounded to extract + load (parse/flatten raw JSON, no business logic); all transformation happens in dbt SQL against the warehouse. | [12] IBM, *ELT vs. ETL: What's the Difference?*; [13] dbt Labs, *Data transformation vs ETL* |
| Pinned, reproducible dependencies | **Partially done** | `requirements.txt` exists but isn't currently version-pinned (just `requests`). Fine for two small scripts; will pin versions before the Spark/dbt dependency set grows, since unpinned versions are a real source of "works on my machine" bugs. | *General Python packaging practice — no single canonical source.* |

## What's explicitly not a goal of this checklist

Not every real-world practice belongs here just because it exists — e.g. multi-region failover, cost-based autoscaling, or data governance/access-control tooling would be actively strange to build for a one-time personal backfill. Leaving them off isn't an oversight; they're not being tracked as "skipped" because they were never in scope to begin with. The line I'm drawing: track things a data engineer would reasonably expect *this specific project* to have an opinion on, not a maximal checklist of everything a large company's data platform might do.
