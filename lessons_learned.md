# Lessons Learned

Generalizable takeaways from this project, distinct from `docs/decisions/` (which records *what* was decided and why, for this project specifically). This is about transferable methodology worth carrying into other work, including interview conversations about how I debug, not just what I built.

## Test your explanation, don't just believe the plausible one (2026-07-31)

**What happened:** found that Manifold's search results seemed to be missing a whole category of markets (sports-linked ones). The obvious, plausible explanation was already sitting right there. We'd *just* fixed a real pagination-instability bug (ADR-0006, duplicate markets from unstable relevance ranking). It would have been easy to assume "same bug, different symptom" and move on.

**What actually happened instead:** tested that exact hypothesis directly. Ran 5 independent full pagination sweeps and checked whether the missing markets showed up in some sweeps but not others (which is what instability would look like). They didn't. Every sweep returned the identical result, zero variance. The obvious explanation was wrong.

That "failed" test wasn't wasted effort. Ruling out the plausible-but-wrong explanation was what forced isolating the real variable (page size, `limit`), which was the actual cause (ADR-0007). If I'd shipped a fix based on the first explanation (more retries, more sweeps), it wouldn't have changed anything, and the real bug (silently missing 37% of the dataset) would still be there, undetected, because the fix would have "worked" by coincidence of not breaking anything, while not actually fixing the real problem.

**The generalizable lesson:** when a bug looks like one you've already seen, that's exactly when to be most suspicious of pattern-matching instead of testing. A quick, direct test that isolates one variable at a time (here: hold everything constant, vary only `limit`) is cheap compared to shipping a fix that doesn't address the real cause. "I ran a test and it disproved my first theory" is a *good* debugging story, not a failed one. It's evidence of a real investigation, not a guess that happened to work.

## Two numbers sharing a name aren't the same comparison (2026-07-31)

**What happened:** compared this project's Brier score to Manifold's published platform-wide number (0.1748) and got 0.0185, dramatically, suspiciously better. It was tempting to report that as the headline result. Instead, dug into *why* the gap was so large, and found the two numbers weren't measuring the same thing at all: Manifold's is trade-weighted (one row per trade, using the average of the market's probability just before and just after that trade, compared against the market's eventual resolution, across the market's entire trading lifetime) and restricted to `BINARY` markets with 15+ traders. Ours was one row per resolved market or answer, using its probability at *resolution time only* (a single snapshot, not a lifetime of trades), and it included `MULTIPLE_CHOICE` answers Manifold's number excludes entirely. Excluding a dominant "easy" bucket brought our number to 0.0437, still nowhere near a real fix, because the underlying unit of analysis was still wrong.

**What actually happened instead:** rebuilt the comparison from the unit of analysis up instead of tuning the existing number. Wrote [`mart_trade_calibration`](../dbt/models/marts/mart_trade_calibration.sql): one row per real trade, `BINARY` markets only, 15+ distinct traders, predicted probability = `(prob_before + prob_after) / 2`, Manifold's own stated definition, quoted from their calibration page, not a guess at it. That produced a materially different number: **0.1305**, not 0.0185. Still better than Manifold's 0.1748, but by a believable margin instead of a suspicious one.

**The generalizable lesson:** a benchmark comparison is only as valid as the match between the two things being compared, and a shared metric *name* ("Brier score") is not evidence of a shared metric *definition*. Before trusting a number that looks flattering (or damning), check what population, grain, and time-window it was actually computed over, not just what it's called. A 10x gap against a credible external benchmark is much more often a sign the two sides are measuring different things than a sign of a real 10x effect. Read the other side's actual methodology and replicate their unit of analysis exactly before drawing a conclusion from the comparison. "I found a suspiciously good number and went looking for why" is the right instinct, and it's a good story to be able to tell in an interview, not something to gloss over in favor of the flattering headline.

## Blaming the new environment is the easy guess, not necessarily the right one (2026-07-31)

**What happened:** containerizing the pipeline for Kubernetes, `pull_bets.py` (and then `pull_markets.py`) started throwing `ConnectionError`/`ReadTimeoutError` mid-run, a read timeout against Manifold's API, with no HTTP response to even check a status code on. The obvious, plausible explanation was sitting right there: this had never happened in months of running the same scripts locally, and the one thing that had just changed was running everything inside Docker Desktop. "Docker's network virtualization is adding latency or dropping connections" would have been an easy story to accept and move on from.

**What actually happened instead:** tested that exact hypothesis directly instead of accepting it. Hit the same Manifold endpoint, with the same query, from the host directly, completely outside any container, in a plain loop. Response times: 17-29 seconds per request, consistently, from the host. That's not a Docker artifact; that's genuine slowness (most likely throttling) from Manifold's `/v0/search-markets` endpoint under rapid, repeated identical queries. The container didn't cause the problem. It just happened to be the first place a script ever made this exact request pattern without a generous-enough timeout and without retry logic to absorb it.

**The generalizable lesson:** when a failure shows up right after introducing something new (a container, a new environment, a new library version), the new thing is the easiest suspect precisely because it's the easiest story. But "easiest to blame" and "actually responsible" are different claims, and only one of them is worth acting on. A five-minute direct test (same request, old environment vs. new one) either confirms the new thing is guilty or clears it, and clearing it matters just as much: it pointed the actual fix at the right place (retry logic + realistic timeouts in the ingest scripts themselves, extracted into a shared `ingest/retry_get.py` used by all three) instead of a wrong one (tuning Docker's network settings, which would have fixed nothing, since the real cause reproduces with no Docker involved at all).

## The same field means different things depending on a market's shape (2026-08-01)

**What happened:** while building `mart_pre_kickoff_calibration` (the pre-kickoff analysis from ADR-0008), the new mart produced far fewer rows than expected. Traced it back to `mart_market_efficiency`'s existing `multiple_choice_predictions` logic, which filters on `resolution in ('YES', 'NO')` at the answer level. That filter looked complete, and it had been passing tests since the mart was first built. It was quietly wrong the whole time.

Manifold's `MULTIPLE_CHOICE` markets resolve in two different shapes, and only one of them sets a per-answer `resolution` field at all. "Independent" markets (the market itself resolves `'MKT'`) let each answer resolve on its own, `'YES'` or `'NO'`, which is the only shape the original logic handled. "Single-select" markets resolve the *market* to one winning `answer_id` and never touch the answer's own `resolution` field, it stays `NULL` forever, even though the market is fully resolved and the winner is completely knowable. Checking `a.resolution in ('YES', 'NO')` silently dropped every answer from every single-select market: 1,310 rows platform-wide, more than the 2,831 predictions the mart already had.

**What actually happened instead:** derived `is_yes` from the market's own `resolution` field for this shape instead of trusting the answer row: `a.answer_id = m.resolution`. Also found two smaller edge cases the same way, by grouping every observed `market.resolution` value and checking what each one meant before writing the fix: `'CANCEL'` (voided, correctly excluded) and `'CHOOSE_MULTIPLE'` (multiple winners, but the winning set isn't captured in what this project pulled, so correctly excluded rather than guessed at). `mart_market_efficiency` went from 2,831 to 3,648 resolved predictions once fixed, all real, previously-silent gaps, not new data. Full numbers in `docs/results.md`.

**The generalizable lesson:** a `NULL` in a field that's usually populated isn't automatically "not applicable" or "not yet resolved." It can mean "this field isn't how this particular row's shape encodes that information at all," and the real answer lives in a different column, possibly on a different table entirely. A test suite that passes doesn't mean the query is complete, only that it's internally consistent with what it happens to already select. The way to catch this is the same instinct as the earlier Brier-score lesson above: when a filter condition looks obviously correct, check what it's silently excluding, not just what it correctly includes. Grouping by every distinct value a "status"-like field actually takes, before writing logic against it, would have caught this on the first pass instead of after the fact.

## The same root cause can bite twice, in a different shape (2026-08-02)

**What happened:** three CI runs in a row failed the moment ADR-0008's kickoff-time work landed, all with the same Spark error: `sportsStartTimestamp cannot be resolved`. `flatten_markets()` selects that column directly, and it's a real field on real markets, so the instinct was to assume the small CI fixture's data was stale and needed a value added to it, the same fix as the last time a fixture-vs-full-dataset mismatch broke CI.

**What actually happened instead:** checked the fixture's 5 markets against the *full* real dataset first, not just against the fixture. All 5 genuinely never carry `sportsStartTimestamp` at all, in the full 621-market dataset too, not just the fixture. That's expected: ADR-0008 already established this field only exists on markets in one specific format, and none of the 5 sampled fixture markets happen to be that format. The fixture wasn't stale. The bug was that `flatten_markets()` assumes the column exists in Spark's *inferred* schema at all, which only holds for the full dataset because, across 621 markets, at least one happens to carry the field. A small sample can come up with zero such markets by chance, and then the column isn't present-but-null in the inferred schema, it's entirely absent, and a direct `.select()` on it throws instead of returning nulls.

This is the same root cause as the earlier `totalLiquidity` BIGINT/DOUBLE bug (`_as_double()`, documented in `spark/flatten_to_parquet.py`'s own docstring): a small sample's inferred schema can't be trusted to match the full dataset's. That first fix handled it for a column's *type*. This one is the same problem one level earlier, a column's very *existence* in the inferred schema. Fixed with a small `_optional_string()` helper: select the real column if Spark's schema has it, otherwise substitute an all-NULL column of the right type, so downstream logic (ADR-0008's matcher, which already treats "no kickoff time" as a valid, expected state) sees exactly what it would see from a real market lacking the field.

**The generalizable lesson:** "the fixture must be stale" is the easy explanation the moment a small-sample test breaks after adding a new field, and it's worth checking against the full dataset before acting on it, the same discipline as the "test your explanation, don't just believe the plausible one" lesson above. Once a project has hit "small samples can disagree with the full dataset's inferred schema" for one reason (a type), it's worth treating that as a named category of risk, not a one-off, and checking new optional fields against it directly: could a small sample plausibly have zero rows carrying this key at all, not just different values for it. A schema-inference bug fixed once by pattern-matching the specific symptom (cast the type) will recur in a different shape (the column disappearing) if the underlying cause (inference over a small sample) isn't the thing that actually gets fixed.

## A second target doesn't test new code, it tests everything the first target was quietly hiding (2026-08-02)

**What happened:** adding Postgres as a second, optional dbt target (ADR-0004) sounded like config work: point a new `profiles.yml` output at a different connection string, done. It wasn't. Running `dbt build --target postgres` against the exact same models that had been passing on DuckDB for weeks surfaced five separate real bugs, one after another, each one something that had been silently true the entire time and never had a reason to matter: DuckDB reads Parquet files directly with no load step, so nothing had ever tested what loading that data into a real table would take. `epoch_ms()` and `try_cast()` are DuckDB functions, not SQL, and nothing had ever forced that distinction to matter either. Same story for `double` as a bare type name, and for how pandas silently drops a boolean column to generic `object` dtype the moment it contains a null. None of these were new code. All of them were pre-existing assumptions a single-adapter project never had a reason to question.

**What actually happened instead:** fixed each one as it surfaced, in the order the build actually failed in, rather than trying to audit the whole codebase for DuckDB-isms up front. That order turned out to matter: `stg_manifold_bets` failing on `epoch_ms` was the first sign, fixing it immediately exposed the next thing (`double` as a contract type), which exposed the next (silently-mistyped booleans). Auditing for "anything DuckDB-specific" in the abstract, before ever running the build, would have meant guessing at what actually mattered instead of following what a real second execution environment actually objected to.

**The generalizable lesson:** portability isn't something you can verify by reading code, only by actually running it somewhere else. A codebase that's only ever run against one database, one OS, one environment necessarily has assumptions baked into it that nobody wrote down, because nobody had to, and the only way to find them is to point something real at the same code and watch what breaks. This is the same shape as the earlier CI-fixture lesson (a small sample hides what a full dataset would show) at a different scope: one adapter hides what a second adapter would show. Worth remembering the next time "just add another target/environment/platform" sounds like config: it's really an audit of every assumption the first one let slide, and the honest way to find them is to run it, not to review it.
