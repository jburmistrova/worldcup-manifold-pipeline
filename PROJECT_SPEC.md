## Data source

**Manifold Markets public API.** A play-money forecasting platform (not real financial stakes; trades happen in virtual "Mana"), used in academic prediction-market research. Public read endpoints need no auth: `/v0/search-markets`, `/v0/market/{id}`, `/v0/bets` for trade-level history. Docs: https://docs.manifold.markets/api

World Cup 2026 had real, meaningful engagement on Manifold: per-match markets, tournament-winner and Golden Boot-style prop markets, some individual markets with $1M+ in historical trading volume. The tournament already happened, so this is backfill/batch analysis over settled markets, same as originally planned.

**ToS check (done 2026-07-30):** confirmed via `docs.manifold.markets/terms` and `docs.manifold.markets/data`. Personal, academic, and non-commercial use of API data (including posting the resulting code/analysis publicly) is explicitly permitted. Only commercial resale or AI/ML training requires a separate paid data license.

## Architecture

1. **Ingest.** Pull every World Cup 2026-related market from Manifold's API, then full bet (trade) history for each. On Manifold, market probability is given directly (0-100%), unlike Kalshi where it's derived from contract price.

2. **Spark (PySpark).** Extract + load only: parse and flatten raw bet-tick JSON at scale (hundreds of markets x tick-level bets is real volume) into clean, partitioned Parquet. Deliberately no business logic here. See [ADR-0005](docs/decisions/0005-elt-not-etl-transformation-lives-in-dbt.md) for why the transformation work below moved to dbt instead of living here.

3. **dbt.** Land Spark's flattened output, build `stg_manifold_bets` -> `int_market_implied_probability` (probability-over-time reconstruction, volume-weighted average probability, repricing-jump detection, all as SQL) -> marts:
   - `mart_match_price_history`: win-probability movement through each match
   - `mart_market_efficiency`: pre-kickoff implied probability vs. actual outcome, across all matches, to measure market calibration
   - `mart_outright_odds_over_time`: how the tournament-winner contract repriced match by match
   - dbt tests: prices bounded 0-100, no duplicate trade IDs, timestamps inside the tournament window

4. **Kubernetes.** Containerize ingestion + Spark + dbt, deploy as a Kubernetes Job on a local cluster (minikube or kind). Framed honestly as a backfill/batch job (tournament's over, this isn't live-polling), but a real, working deployment.

Done (2026-08-01): built the actual pre-kickoff calibration analysis ADR-0008's data made possible, and found a real bug doing it. `int_pre_kickoff_probability` takes each market/answer's implied probability from its last real trade strictly before the validated kickoff time; `mart_pre_kickoff_calibration` compares that to the same outcome `mart_market_efficiency` uses at resolution time. Building it surfaced that `mart_market_efficiency`'s existing multi-choice logic only checked an answer's own `resolution` field, which Manifold leaves `NULL` for "single-select" multi-choice markets (the market itself resolves to a winning `answer_id`, not the answer). That had been silently dropping 1,310 real predictions platform-wide since the mart was first built. Fixed by deriving the winner from the market's own `resolution` field when the answer-level one is absent; `mart_market_efficiency` went from 2,831 to 3,648 resolved predictions, all real data, not new ingestion. Headline result: for the 380 predictions with a validated kickoff time, pre-kickoff Brier score is 0.1708, close to Manifold's own platform-wide 0.1748 and this project's own liquidity-tier range (0.15-0.19); the resolution-time Brier for those same 380 predictions is 0.0008, confirming resolution-time probability mostly just records an already-known outcome rather than measuring genuine calibration. Full mechanism in `lessons_learned.md`, numbers in `docs/results.md`, ADR-0008 updated with a Consequences follow-up.

## Extension beyond original scope: Polymarket, a second platform

Not part of the original core/stretch plan above, added afterward to answer a real question the single-platform pipeline couldn't: does calibration actually differ between Manifold and a real-money exchange.

Done (2026-08-03): verified Polymarket as an eligible data source by reading its actual Terms of Use PDF directly, not a summary (the live page is a JS-rendered app my fetch tooling couldn't read; the user supplied the PDF). The operative clause restricts commercial use by "Capital Market Client" professional entities and market data distributors, not personal research, a materially different, more permissive answer than Kalshi's (ADR-0001). Full reasoning in [ADR-0010](docs/decisions/0010-polymarket-eligible-as-a-future-data-source.md).

Investigated Polymarket's actual API shape empirically before writing ingestion code, the same discipline as every other data-source integration here, and found three real, load-bearing surprises: market/event structure doesn't map 1:1 to Manifold's (an outright-winner "event" splits into dozens of separate binary markets, not one multi-choice market), trades carry a single execution price with no before/after pair, and `/trades` caps at the 10,000 most recent records per market, reachable within hours on a popular market, not enough for pre-tournament history. Switched to `/prices-history` (a time-chunked, not count-capped, endpoint) as the real reconstruction source instead. Full findings in [ADR-0011](docs/decisions/0011-polymarket-api-shape-and-full-history-pricing.md).

Done (2026-08-03): built a canonical cross-platform schema (`int_all_market_ticks`) so `int_market_implied_probability`'s actual reconstruction logic doesn't need to know which platform a row came from. Manifold's real `prob_before`/`prob_after` pairs pass through unmodified; Polymarket's are derived via `LAG(price)`, validated empirically as sound for Polymarket specifically (no cross-answer coupling like Manifold's shared-liquidity `MULTIPLE_CHOICE` markets have) after briefly considering, and rejecting, applying the same derivation to Manifold too. Two real bugs caught building this: a synthesized Polymarket `bet_id` that collided across markets (row_number() resets per partition, not globally unique), and a silent `TIMESTAMP WITH TIME ZONE` vs `TIMESTAMP` mismatch between DuckDB's `to_timestamp()` and Manifold's own UTC-naive columns. Validated on a real 60-market sample before scaling to the full dataset (488 events, 6,358 markets, 4,378,920 trades, 3,209,795 price points). Found and fixed a second real bug scaling up: `retry_get.py` didn't retry HTTP 408, a genuinely transient server timeout that only appeared 1,125 markets into a 6,358-market run, a small sample never reached. Full reasoning in [ADR-0012](docs/decisions/0012-cross-platform-canonical-trade-schema.md), the recurring lesson in `lessons_learned.md`.

**A real regression caught before it shipped:** once Manifold's own core marts started reading through the shared union model, a plain `dbt build` broke outright the moment Polymarket's raw data wasn't present, even for someone only running the original Manifold pipeline. Fixed by gating every Polymarket-dependent model behind `INCLUDE_POLYMARKET` (default off, opt-in via `dbt build --vars` or the env var of the same name), verified both ways: 101/101 tests passing with Polymarket absent, 121/121 with it included.

Done (2026-08-04): built the actual real-money-vs-play-money comparison, as a deliberate, explicit exception to this project's own DE scope (a bootstrap significance test was built once before for a different comparison, then removed for veering into data science; asked directly this time, chose to build it anyway). Scoped to both platforms' outright World Cup winner markets (a real, comparable event with unambiguous ground truth), compared at each team's last implied probability strictly before the tournament itself started, not resolution-time (which the project's own earlier finding showed is close to meaningless for calibration). Result: no statistically significant difference (bootstrap 95% CI [-0.0402, 0.0422], p≈0.83), though the sample is small and low-power by construction (47 and 50 predictions, one true positive each). Checked the result against the actual published literature rather than assumed it was novel: the classic Servan-Schreiber/Wolfers/Pennock/Galebach (2004) NFL study found the same direction with far more power; a more recent, methodologically closer iPredict study found a significant real-money advantage in direct same-event comparisons. Separately built a purely descriptive team-by-team comparison (no significance test): 46 of 50 teams matched within a few percentage points, with the largest disagreements concentrated at the top of the market (France, Argentina), Manifold pricing favorites higher than Polymarket. Corrected the "play money" framing along the way after checking Manifold's actual Mana policy: cash buys Mana, but Mana can't convert back to cash under any circumstance except a fixed-rate charity donation, so the real distinction is two-way-convertible profit (Polymarket) vs. one-way-convertible spend-only currency (Manifold), not "real vs. fake." Full reasoning, citations, and the correction in [ADR-0013](docs/decisions/0013-platform-calibration-comparison-as-a-deliberate-ds-exception.md) and `docs/results.md`'s addendum.

Done (2026-08-07): wired Polymarket into CI. New fixture ([`tests/fixtures/raw/`](tests/fixtures/raw/)): 2 real events, chosen for naturally small trade/price counts rather than truncated, not a bigger sample cut down (same discipline as the Manifold fixture and ADR-0006), a 3-market negRisk-grouped resolved pair (exercises the `market_id`/`answer_id` grouping derivation, the `YES`/`NO` resolution decode, and the Yes-side trade filter, since it has real trades on both `outcomeIndex` values) and a standalone unresolved market (exercises the un-grouped, `answer_id IS NULL` path, and the real edge case of a market with trades but no price-history rows at all). Verified locally, in an isolated copy of the repo so the real 10GB `data/raw/` wasn't touched: `dbt build` (default) still 101/101, `INCLUDE_POLYMARKET=true dbt build` now 121/121 with real nonzero row counts through `stg_polymarket_markets`/`_trades`/`_prices` and `int_all_market_ticks`, not just tests passing vacuously on empty tables. `.github/workflows/ci.yml` now flattens and builds the gated Polymarket path on every push, DuckDB only, since `load_parquet_to_postgres.py` has no Polymarket support, a deliberate scope boundary, not an oversight. Found, in the process, that `mart_platform_calibration_comparison` still builds to zero rows in CI regardless: it hardcodes the real, full-scale outright-winner market IDs for both platforms, and no fixture, old or new, contains those specific markets, the same "known gap" shape as the pre-existing Manifold kickoff-time marts, now hit a third time. Documented, not fixed, in `docs/data_engineering_best_practices.md`, matching how the project already treats that class of gap.
